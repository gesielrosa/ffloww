# .specs — ffloww flow conventions

The contract the `/flow:*` commands follow. Each phase reads this file, the ticket's
`state.md`, and its `context.md` before acting.

## The record

`.specs/<ticket-id>/` is the flow's memory. Whatever shapes later work (an answer, a
decision, a constraint) goes into the ticket's files as it happens, so any phase can
start in a fresh context.

- `state.md` — phase, steps, navigation log; the single source of truth
- `understanding.md` — problem, scope, acceptance criteria, design notes
- `context.md` — what the developer adds beyond the ticket and the code (`/flow:context`)
- `discoveries.md` — code map and options · `decisions.md` — ADR log and regressions
- `plan.md` — the breakdown · `steps/NN-<slug>.md` — one spec per step
- `verification.md` — whole-ticket check · `evidence/` — proof logs · `assets/` — design exports

`.specs/PROJECT.md` is the project profile: what every ticket here needs and none
should learn twice (the proof commands with their flags and durations, where a fast proof
ends, the commit policy, the PR format). `/flow:plan` reads it and adds what its
baseline shows.

Flow: start → understand → design (if any) → explore → plan → execute ⇄ verify → ship.
Short route: start → understand → design (if any) → plan → execute → ship.

## Commands and the ticket

Each phase is a command the developer types: `/flow:<phase> <ticket-id>`, and the
developer runs the next one when ready. The ticket id comes from the command's argument;
without one, use the only ticket in progress under `.specs/`, or ask which.

## Phase boundaries

A phase ends once whatever the developer said that shapes later work is in the ticket's
files. It then names the next command (the `Next:` line the state script prints) and
advises on the session:
- up to the plan (understand, design, explore), the next phase builds on this
  conversation, so it continues in this session unless the session has grown long;
- from the plan on (plan → execute, step to step, verify → ship), each phase works from
  self-contained specs, so `/clear` comes first.

## State

`state.md` changes only through the flow's state script (`state.js`: `show`, `diff`,
`fresh`, `phase`, `set`, `add-step`, `remove-step`, `step`, `log`); the plugin
blocks hand edits. Phases move forward freely; moving back is a regression and needs a reason,
recorded in `decisions.md` too. A step moves `todo → in-progress → proven` (approved at
its gate) `→ done` (committed), one at a time. Before the gate, a step's proof passes
or fails; only the developer's approval makes it `proven`.

How the ticket is committed is the developer's choice; a new ticket takes the profile's
Policy. By default each step is committed before the next one starts
(`commit: per-step`). With `state.js set commit at-end`, steps stay `proven` while
the next ones are built, and one commit after the last gate makes them all `done`.
Either way a step's change stands alone: the state script snapshots the working tree
when the step starts, and `state.js diff <step-id>` prints the step's files and its
`git diff` from there.

A small, clear change can take the **short route**, when the developer chooses it
(`state.js set route short`): the plan maps the change itself instead of a separate
explore, and the last step's gate leads to ship, without a whole-ticket verify.

## Roles

- The developer decides: the approach, the slicing, and whether each proof holds.
  Someone else with a say in the approach (the ticket's owner, the area's) hears the
  decision before the build: `/flow:plan` drafts a summary for the developer to send.
- The main session talks to the developer, opens the gates, and changes state.
  Subagents build or read, then report back; a report is a lead to check.
- A step's `Executor` line says who builds it: `delegate` (a subagent on Sonnet),
  `delegate-light` (on Haiku, for mechanical steps), or `inline` (the main session).

## Gates — make it prove it

- Proof is raw evidence recorded by the proof runner (`run_proof.js`): command, exit
  code, real output; or a screenshot path. Numbers, not opinions.
- A proof's exit code is its verdict: each proof command exits non-zero exactly when its
  criterion fails. A proof that passes on another code runs plain with the runner's
  `--expect <code>` (a search that must find nothing: `grep` exits 1, and 2 or 127
  when it could not look). The runner keeps the full output, so no `| tail` or
  `; echo $?` is needed, and it notes what can hide the verdict: a command chained with
  `;`, `||` or a pipe (the exit code is its last part's), a command negated with `!`,
  a command the shell did not find. A note goes to the gate with the result.
- The runner runs each command from the project root, in bash where the machine has one
  (Git Bash on Windows), without your terminal's profile: an alias or a function
  defined there is not a command here.
- A proof has to be able to fail. A Proof command the plan marks `red first` (new
  behavior, fast enough to run twice) runs once before the change, with the runner's
  `--red`, and has to fail there; a proof that passes without the change proves nothing
  about it. Guards that are green before and after (lint, typecheck, the existing
  suite) carry no mark.
- A step's proof is sized to the step: the tests of what it changes, and the guards fast
  enough to run every time. A slow run (the whole suite of a large project, a build, an
  end-to-end run) runs once for the ticket: at `/flow:verify`, or in the last step on
  the short route. Where fast ends is the developer's line, kept in the profile.
- Every acceptance criterion has a proof or a named gap. The plan's **Criteria and
  proof** table says how each one is shown (`runtime`, `test`, `construction`,
  `manual`) and by which step's command; `/flow:verify` runs it as written, and a
  `gap` is the developer's to accept.
- Evidence is about a tree. The runner records the working tree each proof ran on, and
  `state.js fresh` says how far the branch is behind its base, whether the two would
  merge, and which proofs predate the tree as it is now. `/flow:verify` reads it
  before the whole-ticket proofs and `/flow:ship` before the draft: work that changed
  after its proof, or whose base moved under it, is said at the gate.
- The developer grades the evidence at the step's `Gate`; the assistant presents it
  and records the decision. Recorded evidence is immutable: a new result is a new run.
- A review finding leaves the gate with an outcome, written in the step's `Gate`:
  fixed, accepted, rejected, or deferred to a later step, whose spec then carries it as
  a check of its own.
- Proofs read credentials from environment variables; the runner masks the secrets it
  recognizes before recording.

## Git & PR

Read git freely (`status`, `diff`, `log`, a `fetch` of the base before it is
compared). Commits, branches, merges, pushes and PRs are the developer's: `/flow:execute` drafts commit messages and `/flow:ship` a PR/MR draft, in
the developer's conventions, for whatever VCS host they use.

Principles: give it context · explore before build · you architect, it types · small
steps · make it prove it · own it.
